# 3. Separe Local-Only de Cloud

O Mobile deverá suportar dois estados claramente distintos.

## Modo A — Somente neste aparelho

O usuário poderá começar a utilizar o aplicativo sem:

* Criar conta;
* Fazer login;
* Possuir família no cloud;
* Acessar Firebase;
* Estar conectado à Internet.

Nesse modo, o usuário poderá cadastrar localmente:

* Familiar/Paciente;
* Consultas;
* Medicamentos;
* Exames;
* Documentos/Receitas.

Os dados permanecerão no armazenamento privado local do aplicativo.

## Modo B — Sincronizado

Posteriormente, por decisão explícita do usuário, o workspace local poderá ser vinculado à plataforma cloud Saúde Familiar.

Nesse momento poderão existir simultaneamente:

* Dados criados anteriormente no Mobile;
* Dados já existentes no Desktop/cloud;
* Dados equivalentes;
* Dados diferentes;
* Possíveis conflitos.

O contrato precisa prever essa transição sem assumir que ela será trivial.

## Correspondência Local → Cloud

Analise explicitamente o seguinte cenário:

Um usuário utiliza o Mobile sem conta e cadastra localmente:

`João da Silva — 10/05/1950`

Posteriormente, ativa a sincronização e entra em uma família cloud que já possui um paciente que potencialmente corresponde a esse mesmo João da Silva.

Defina uma estratégia para:

* Detectar possíveis correspondências;
* Apresentá-las ao usuário;
* Permitir associar o paciente local ao paciente cloud existente;
* Permitir manter ambos separados quando forem pessoas diferentes;
* Evitar duplicação acidental;
* Tratar os registros clínicos locais associados ao paciente;
* Tratar diferenças entre os dados cadastrais locais e cloud.

**Não faça merge automático de pacientes baseado apenas em nome, data de nascimento ou heurísticas semelhantes.**

O sistema pode sugerir uma possível correspondência, mas uma fusão/associação de identidades de pacientes deve exigir confirmação explícita do usuário quando não existir um identificador confiável comum.

Explique também como medicamentos, consultas, exames e documentos locais desse paciente seriam tratados após a associação.

## Regra obrigatória para armazenamento local

O banco local, como SQLite, deve armazenar **somente metadados e a referência/URI/caminho para o arquivo no armazenamento privado do aplicativo**.

**Não armazene imagens, PDFs ou outros documentos como Base64 ou binários/BLOBs dentro das tabelas SQLite nesta arquitetura inicial.**

A arquitetura conceitual deve ser:

```text
Registro SQLite
    │
    ├── metadados
    ├── localFileUri
    └── estado do arquivo
             │
             ▼
Armazenamento privado de arquivos do aplicativo
             │
             ▼
foto / PDF / documento
```

Analise também:

* O que acontece se o registro SQLite existir e o arquivo tiver desaparecido;
* O que acontece se o arquivo existir mas os metadados estiverem inconsistentes;
* Como detectar arquivo corrompido;
* Como reexecutar upload sem duplicação;
* Quando remover o arquivo local após sincronização, se isso for desejável;
* Como evitar que arquivos clínicos sejam expostos em áreas públicas/galeria do aparelho.

A arquitetura atual não deve impedir uma futura evolução de Receita para um modelo estruturado.
